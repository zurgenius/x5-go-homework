# Сервис заказов

Учебный REST API на Go: создание и просмотр заказов, изменение статуса и история переходов. Данные хранятся в памяти и теряются после остановки сервера.

## Запуск

Требуется Go 1.22 или новее. Команды выполняются из папки проекта:

```bash
go run ./cmd/api
```

По умолчанию сервер слушает `:8080`. Адрес можно изменить через переменную `HTTP_ADDR`, например `HTTP_ADDR=:8081 go run ./cmd/api`.

Swagger UI: [http://localhost:8080/swagger/index.html](http://localhost:8080/swagger/index.html).

## API

| Метод | Путь | Описание | Успех |
|---|---|---|---:|
| GET | `/health` | Проверка сервиса | 200 |
| POST | `/api/v1/orders` | Создать заказ | 201 |
| GET | `/api/v1/orders` | Получить список | 200 |
| GET | `/api/v1/orders/{id}` | Получить заказ | 200 |
| PATCH | `/api/v1/orders/{id}/status` | Изменить статус | 200 |
| GET | `/api/v1/orders/{id}/history` | Получить историю статусов | 200 |

Пример создания:

```bash
curl -X POST http://localhost:8080/api/v1/orders \
  -H 'Content-Type: application/json' \
  -d '{"items":[{"name":"Keyboard","quantity":1,"price":500000}]}'
```

Подставьте `id` из ответа, чтобы изменить статус и получить историю:

```bash
curl -X PATCH 'http://localhost:8080/api/v1/orders/<ORDER_ID>/status' \
  -H 'Content-Type: application/json' -d '{"status":"processing"}'
curl 'http://localhost:8080/api/v1/orders/<ORDER_ID>/history'
```

Цена указывается целым числом в минимальных денежных единицах, например в копейках. Заказ должен содержать хотя бы одну позицию; название не может быть пустым, количество и цена должны быть больше нуля. Сумма вычисляется сервером. ID — UUIDv7, его создаёт репозиторий.

UUIDv7 выбран с расчётом на будущий переход на PostgreSQL: идентификаторы можно сохранить при переносе данных в поле типа `uuid` и генерировать независимо от конкретного хранилища.

Новый заказ получает статус `new`. Допустимые переходы: `new → processing`, `new → cancelled`, `processing → completed`, `processing → cancelled`. Последние два статуса конечные. При создании и каждом переходе сохраняется запись в истории.

Ошибки возвращаются в формате `{"error":"...","code":"..."}`: некорректный запрос или данные — 400, заказ не найден — 404, недопустимый переход — 409, внутренняя ошибка — 500. Внутренние детали ошибки клиенту не передаются.

## Устройство и проверки

`handler` разбирает JSON и формирует ответы, `service` проверяет бизнес-правила, `repository` хранит заказы в памяти. HTTP-запросы логируются через `slog`; middleware восстанавливает сервер после паники обработчика. Теги `validate` в HTTP-моделях используются для генерации Swagger; проверки выполняются в коде сервиса.

Для HTTP-запросов и ответов в `internal/handler/models.go` определены отдельные DTO. Обработчик преобразует DTO запроса во внутренние модели перед вызовом сервиса, а результат сервиса — в DTO ответа.

```bash
go test ./...
go test ./internal/service/... -cover
go vet ./...
go build ./...
gofmt -l cmd internal
```

После изменения Swagger-аннотаций документацию можно обновить командой:

```bash
go run github.com/swaggo/swag/cmd/swag@v1.16.6 init -g cmd/api/main.go -o docs
```
