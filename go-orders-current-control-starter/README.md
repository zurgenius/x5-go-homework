# Текущий контроль № 1: backend-сервис заказов

Реализация первого этапа итогового проекта по курсу Go.

## Цель

Разработать первый рабочий прототип backend-сервиса заказов: от предметной модели и бизнес-логики до HTTP REST API, документации и модульных тестов.

На этом этапе данные хранятся в памяти приложения. PostgreSQL, миграции, JWT, Docker, интеграционные и API-тесты будут добавлены после изучения соответствующих тем.

## Что реализовано

Сервис предоставляет REST API заказов, хранит данные в памяти, ведёт историю статусов и записывает структурированные логи. Документация Swagger доступна вместе с приложением; бизнес-логика покрыта модульными тестами.

## Задание

Реализуйте базовую версию backend-сервиса заказов на Go. Сервис должен создавать заказы, возвращать один заказ и список заказов, изменять статус и выдавать историю изменения статусов.

Обязательные составляющие:

- слои `handler`, `service`, `repository`;
- in-memory-хранилище;
- HTTP REST API и JSON;
- предметные ошибки и корректные HTTP-коды;
- структурированные логи через `log/slog`;
- middleware логирования и восстановления после паники;
- Swagger/OpenAPI;
- модульные table-driven тесты слоя `service`;
- покрытие пакета бизнес-логики не менее 80%;
- заполненный README репозитория.

## Модель данных

### Позиция заказа

```json
{
  "name": "Keyboard",
  "quantity": 1,
  "price": 500000
}
```

`price` хранится целым числом в минимальных денежных единицах, например в копейках.

### Заказ

Заказ содержит:

- уникальный идентификатор;
- непустой список позиций;
- рассчитанную итоговую стоимость;
- текущий статус;
- дату создания;
- историю статусов.

### Статусы и переходы

Допустимые статусы:

- `new`;
- `processing`;
- `completed`;
- `cancelled`.

Новый заказ автоматически получает статус `new`. Допустимы только переходы:

- `new → processing`;
- `new → cancelled`;
- `processing → completed`;
- `processing → cancelled`.

Статусы `completed` и `cancelled` являются конечными.

## Валидация

При создании заказа необходимо проверить:

- наличие хотя бы одной позиции;
- непустое название каждого товара;
- `quantity > 0`;
- `price > 0`.

Итоговая стоимость рассчитывается как сумма `price × quantity` по всем позициям.

## Обязательные эндпоинты

| Метод | Путь | Назначение | Успешный код |
|---|---|---|---:|
| GET | `/health` | Проверка доступности сервиса | 200 |
| POST | `/api/v1/orders` | Создание заказа | 201 |
| GET | `/api/v1/orders` | Получение списка заказов | 200 |
| GET | `/api/v1/orders/{id}` | Получение заказа | 200 |
| PATCH | `/api/v1/orders/{id}/status` | Изменение статуса | 200 |
| GET | `/api/v1/orders/{id}/history` | Получение истории статусов | 200 |

Пример создания заказа:

```json
{
  "items": [
    {
      "name": "Keyboard",
      "quantity": 1,
      "price": 500000
    }
  ]
}
```

Пример изменения статуса:

```json
{
  "status": "processing"
}
```

## Ошибки и HTTP-коды

| Ситуация | Код |
|---|---:|
| Некорректный JSON или невалидные данные | 400 Bad Request |
| Заказ не найден | 404 Not Found |
| Недопустимый переход статуса | 409 Conflict |
| Неожиданная внутренняя ошибка | 500 Internal Server Error |

Единый формат ответа:

```json
{
  "error": "status transition is not allowed",
  "code": "INVALID_STATUS_TRANSITION"
}
```

Внутренние детали ошибок не должны возвращаться клиенту. Для определения причины используйте `errors.Is` и при необходимости `errors.As`.

## Архитектура

```text
HTTP request → handler → service → repository → in-memory storage
```

- `handler` читает HTTP-запрос, валидирует его формат, вызывает сервис и преобразует результат в HTTP-ответ;
- `service` содержит бизнес-правила и не зависит от конкретного хранилища;
- `repository` хранит и возвращает данные;
- зависимости передаются через конструкторы и интерфейсы.

Структура проекта:

```text
cmd/api/main.go
internal/order/
internal/service/
internal/repository/memory/
internal/handler/
docs/
```

Структуру можно изменить, если зоны ответственности останутся разделены и решение можно обосновать.

## Логирование и middleware

Для каждого HTTP-запроса структурированный лог должен содержать:

- `method`;
- `path`;
- `status`;
- `duration`;
- `request_id`.

Recovery middleware должен перехватывать панику, записывать её в лог и возвращать безопасный JSON-ответ с кодом 500, не завершая работу сервера.

3. пустое название товара;
4. нулевые и отрицательные `quantity` и `price`;
5. расчёт итоговой стоимости;
6. получение существующего и отсутствующего заказа;
7. получение списка заказов;

10. запрет изменения конечного статуса;
11. добавление записей в историю;

Требования к тестам:

- `testing` и `testify/assert` или `testify/require`;
- table-driven tests;

Интеграционные тесты и тесты HTTP API на текущем контроле не являются обязательными.

## Реализация

Сервис хранит заказы только в памяти: после перезапуска данные теряются. `HTTP_ADDR` задаёт адрес сервера (по умолчанию `:8080`). Swagger UI доступен по адресу `http://localhost:8080/swagger/index.html`. Для обновления документации после изменения аннотаций:

```bash
go run github.com/swaggo/swag/cmd/swag@v1.16.6 init -g cmd/api/main.go -o docs
```

Создание заказа и изменение статуса:

```bash
curl -X POST http://localhost:8080/api/v1/orders -H 'Content-Type: application/json' -d '{"items":[{"name":"Keyboard","quantity":1,"price":500000}]}'
# Подставьте UUID из ответа на создание заказа.
curl -X PATCH 'http://localhost:8080/api/v1/orders/<ORDER_ID>/status' -H 'Content-Type: application/json' -d '{"status":"processing"}'
curl 'http://localhost:8080/api/v1/orders/<ORDER_ID>/history'
```

Некорректный JSON, неизвестные поля, пустое название и числовое переполнение стоимости отклоняются с кодом 400. Статусы, не входящие в перечень допустимых, также возвращают 400; известный, но недопустимый переход возвращает 409. Изменения статусов сериализуются внутри одного экземпляра сервиса.

Идентификаторы заказов — UUIDv7. Репозиторий назначает ID и время создания, а также время новых записей истории.
